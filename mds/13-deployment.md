# Deployment

The hard requirement: a clean clone builds and runs the same way it deploys, and the live URL survives a cold start and comes up healthy. A deploy that is down, or a build that fails from a fresh checkout, is the most common way an otherwise sound service fails review.

---

## Container

Multi-stage Dockerfile.

```
stage 1  builder   install build deps, resolve and install dependencies into a venv
stage 2  runtime   slim base, copy the venv, copy app, non-root user, entrypoint
```

| Property | Choice | Why |
|---|---|---|
| Base | `python:3.13-slim` | Pinned minor version. `latest` makes a reproducible build impossible. |
| Dependencies | Lockfile, hash-pinned, installed in the builder | A float on a transitive dependency is a build that works today and fails at review |
| User | Non-root, created in the image | No reason for a web process to be root |
| Build cache | Dependencies copied and installed before application code | Code changes rebuild in seconds |
| Entrypoint | Script that runs migrations, then execs uvicorn | `exec` so uvicorn is PID 1 and receives SIGTERM directly |
| Port | From `$PORT`, defaulted | Render assigns it |
| Healthcheck | `HEALTHCHECK` hitting `/healthz` | Liveness, not readiness — a healthcheck that touches the database restarts a healthy process during a database blip |
| Image contents | No tests, no `.git`, no local env files | `.dockerignore` enforced |

`docker-compose.yml` brings up Postgres and the service for local work with one command — which matters here, because this machine has neither Postgres nor Docker installed yet, and the compose file is what makes that a one-step fix rather than a setup document.

### Migrations on startup

The entrypoint runs `alembic upgrade head` before starting the server, then `exec`s uvicorn.

Honest trade-off: with multiple instances, concurrent migrations race. Alembic's version table makes this safe for a single migration path (the loser finds nothing to apply), but a long migration during a rolling deploy is a real hazard. For a single instance it is the simplest thing that cannot be forgotten, which is worth more than elegance here. Recorded as RISK-005; the upgrade path is a separate pre-deploy release phase.

## Topology

```
          internet
             │ TLS, platform-terminated
             ▼
   Render Web Service  (Docker)
             │ private network
             ▼
```

`render.yaml` declares both, so the deployment is reproducible from the repository rather than from console clicks.

| Setting | Value |
|---|---|
| Service type | Web, Docker runtime |
| Health check path | `/readyz` — the platform should route traffic only to an instance that can serve it |

| Instances | 1 on the free tier; the design supports N |
| Database | Managed Postgres 16, private networking |

## Configuration

Every value is an environment variable read by `core/config.py`. No defaults for secrets, and startup **fails loudly** if a required secret is absent — a service that boots with a default signing key is worse than one that refuses to boot.

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | From the managed database; never in the repository |
| `JWT_SECRET` | Generated by the platform; no default |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Idempotent admin bootstrap |
| `ACCESS_TOKEN_TTL_SECONDS`, `REFRESH_TOKEN_TTL_SECONDS`, `GUEST_TOKEN_TTL_SECONDS` | Token lifetimes |
| `DEFAULT_PER_USER_LIMIT`, `DEFAULT_HOLD_TTL_SECONDS` | Domain defaults |
| `DB_POOL_MIN`, `DB_POOL_MAX`, `DB_ACQUIRE_TIMEOUT_SECONDS` | Pool sizing — see [11-scalability.md](11-scalability.md) |
| `DB_STATEMENT_TIMEOUT_MS`, `DB_LOCK_TIMEOUT_MS`, `DB_IDLE_TXN_TIMEOUT_MS` | Session guards |
| `RATE_LIMIT_ENABLED`, `RATE_LIMIT_<CLASS>_*` | Per-class ceilings, tunable without a redeploy |
| `AUDIT_QUEUE_MAX`, `AUDIT_BATCH_SIZE`, `AUDIT_FLUSH_INTERVAL_MS` | Audit write path |
| `SWEEPER_INTERVAL_SECONDS`, `SWEEPER_BATCH_SIZE` | Hold expiry |
| `GAUGE_REFRESH_SECONDS`, `GAUGE_MAX_SHOWS` | Metric refresh and cardinality cap |
| `IDEMPOTENCY_WAIT_MS`, `IDEMPOTENCY_STALE_SECONDS`, `IDEMPOTENCY_RETENTION_HOURS` | Key lifecycle |
| `LOG_LEVEL`, `LOG_SAMPLE_DEBUG` | Log volume |

Startup logs the resolved configuration with secrets redacted, so what a running instance actually believes is recoverable from its first log lines rather than inferred.

Startup also validates relationships, not just presence: guest token lifetime must exceed hold TTL plus a margin, pool max must not exceed the database ceiling, and the acquire timeout must exceed the expected queue drain. Each failure refuses to boot with a specific message. A misconfiguration that only manifests as a 503 under load is far more expensive than one that fails at boot.

## Cold start

Render's free tier spins a service down after idle. The first request then pays container start, migration check, pool warm-up, and first-query latency.

| Mitigation | Detail |
|---|---|
| Fast boot | No work in the import path; the pool is created in the lifespan handler |
| `/readyz` as the gate | Platform routes traffic only when the database is genuinely reachable |
| Burst script warms first | Phase 0 polls `/readyz` until ready before measuring — otherwise a cold start is recorded as load |
| Pool pre-warm | `DB_POOL_MIN` connections opened at startup so the first request does not pay connection setup |
| Documented in the README | A reviewer hitting a spun-down URL sees the first request take seconds; saying so prevents it being read as a fault |

Recorded as RISK-001. The free tier's other constraint — a managed free database expiring after a fixed window — is tracked in the ledger with the recreation procedure, because an expired database is a live URL that returns 503 to a reviewer.

## Deploy procedure

1. Push to `main`; CI runs lint, types, unit, integration, concurrency at reduced scale, and a container smoke test from a clean checkout.
2. Render builds the image and deploys on green.
3. Entrypoint applies migrations, then starts uvicorn.
4. Platform polls `/readyz` and routes traffic only once ready.
5. Post-deploy verification, every time: `/healthz`, `/readyz`, `/metrics`, create a throwaway show, reserve against it, confirm the invariant, check the startup log line for the resolved configuration.
6. Run the burst script against the live URL before declaring the deploy good.

Step 5 is not optional. "It deployed" and "it works" are different claims, and only the second one counts.

## Rollback

Redeploy the previous image from the platform's history — the fastest path, and the default.

Migrations are forward-only, so a rollback across a schema change needs the old image to be compatible with the new schema. The discipline that makes this true: schema changes are **additive within a release**. A column is added and populated in one release and only required in the next; a column is stopped being written in one release and dropped in a later one. A migration that both adds a constraint and depends on it in the same release is not rollback-safe, and is split.

## Runbook

| Symptom | First check | Likely cause | Action |
|---|---|---|---|
| `/readyz` 503 | `checks.database.error` | Database down, credentials rotated, connection ceiling | Verify the database; check `db_pool_waiting` |
| 5xx on reserve | `unhandled_exceptions_total`, error logs by request id | A genuine bug, or pool exhaustion | A pool cause is a config fix; anything else is a code defect |
| Invariant mismatch sustained | Counts query versus gauges | Divergent effective-status expression, or a real break | Compare the three usages; check for a `uq_seat_active_claim` violation |
| Backstop index violation | `error` logs for that constraint | The guarded claim has a bug | Page. The service is selling seats twice. |
| Deadlock logged | The two statements involved | A new path violates the lock order | Page. The ordering argument in [04](04-concurrency-and-atomicity.md) is wrong. |
| Seats stuck held | `hold_sweeper_last_run_timestamp` | Sweeper stalled | Not urgent — expiry is lazy in the claim predicate, so seats stay bookable — but state reads are stale |
| Audit dropping | `audit_queue_depth` | Writer stalled or database slow | Raise batch size; check write latency |
| 429s during a burst | `rate_limited_total{route_class}` | Ceiling too low for the traffic shape | Raise the env ceiling; no redeploy required |
| Cold-start timeouts | Platform logs | Idle spin-down | Expected on the free tier; warm before measuring |

Every row starts from a signal that exists. A runbook entry whose first step is "add logging" is a gap in [10-observability.md](10-observability.md), not a runbook entry.

## README contents

The README is what a reviewer reads first, and it must make a clean checkout work without this document:

1. What the service is, and the live URL.
2. Run locally in one command — `docker compose up`.
3. Run without Docker, including the Homebrew Postgres path, since neither Docker nor Postgres is assumed present.
4. The burst script: `./burst.sh <BASE_URL>`, its flags, and an annotated sample output.
5. Auth quickstart: get a guest token, create a show as admin, reserve, confirm — as copy-pasteable `curl`.
6. The documented semantics a reviewer will test: all-or-nothing multi-seat, hold-then-confirm, idempotency behaviour including same-key-different-body.
7. Metrics and logs access, and what to watch during a burst.
8. Environment variables, with the free-tier cold-start caveat stated plainly.
9. A pointer to `mds/00-overview.md` for the design, and to `WRITEUP.md` for the decisions.
